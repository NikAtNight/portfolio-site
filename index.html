What I do

Most engineers use AI coding tools. I engineer the system around them.

My day-to-day setup is a multi-model fleet. Claude orchestrates, Codex implements, and each task goes to the cheapest model tier that can handle the judgment it needs. The interesting part isn't the models. It's everything wrapped around them: write leases so two agents never fight over a worktree, acceptance tests frozen before the implementer sees them, review pipelines where every finding gets an explicit verdict of confirmed, plausible, or refuted, and a permission model where committing doesn't imply pushing and pushing doesn't imply opening a PR.

None of that came from theory. It came from watching agents claim work was done when it wasn't, then building the gate that catches it next time. My core belief after doing this for a while: anything only a human can judge is either real judgment or a missing gate, and most of it is the second kind.

Case study: the agent fleet

The centerpiece is a workflow package I maintain as its own versioned repo. It defines how autonomous agents on my machine plan, delegate, verify, and report, and a sync script generates the copies every tool actually loads. Core rules stay repo-agnostic; anything tied to a specific codebase lives in per-repo files so the general rules don't rot.

Why it exists

One ordinary review prompt once spawned 5 subagents that recursively spawned 928 more. 932 transcripts, 367 MB, 143 rate-limit events, from a single session. The lesson I took wasn't "be more careful." It was that prose guidance doesn't constrain anything. Caps on delegation depth and concurrency now live in harness config, where an agent can't talk its way past them.

The kanban board that runs itself

To make dispatch real, I forked an open-source agent gateway and built the enforcement layer it was missing. Along the way I found the clone was shallow and 508 commits behind upstream, so I rebased onto the real mainline first. The fork now has checkpointing with claim fencing (a successor can't grab a card until its predecessor's process actually exits), a fail-closed capability handshake between dispatcher and workers, comment-driven wake for blocked cards, and workspace leases handed out at dispatch time instead of discovered as conflicts at runtime.

Before calling the branch clean, I ran a differential test sweep: branch and base produced identical failure sets, roughly 605 pre-existing environmental failures on both sides and zero caused by my changes. That distinction is the whole job. A green suite proves little; an unchanged failure set proves the diff.

I also made a deliberate architecture call: the fork is the product. Upstreaming individual pieces is opportunistic, done only to shrink the diff I carry. I'd rather own the rebase cadence than water down the design to fit someone else's roadmap.

Case study: the evidence audit

I mined every agent transcript on my machine, across four different tools, to answer one question: do my agents actually follow the rules I wrote, or do I just believe they do?

The first pass produced numbers I almost shipped. Then an independent review found the methodology was broken, so I threw it out and did it again. Fan-out lanes wrote full replay copies of parent transcripts, inflating 180 files into what was really about 42 distinct threads. One tool logged every user prompt twice. About 76% of sessions were machine-dispatched briefs, not me. Counting complaints with regex over user text produced mostly false positives, so I measured assistant-side actions instead.

The corrected findings, each verified by hand:

Zero unauthorized commits or pushes

Across 460 commits and 281 pushes, every one traced to explicit authorization. All 15 flagged sessions cleared on manual review.

26 sessions claimed done without running a test

Substantial sessions that wrote files, reported success, and never verified. This is the failure mode I now design against hardest.

7 of 43 installed skills had ever been invoked

So I cut the other 36. Tooling earns its place with usage evidence or it goes.

The audit also kept me honest about my own claims. The instruction files were only written mid-period, so a corpus spanning the months before can't prove the current rules work. I flagged that limit in the findings instead of quietly rounding up.

Tools I built because nothing else did the job

pi-ui

TypeScript, node-pty, xterm headless. No build step.

A terminal session browser and multiplexer. It scans the on-disk transcript stores of three different agent CLIs, groups sessions by project in a sidebar, and resumes any of them live in the right pane over a PTY. Sessions keep running detached in the background.

swarm review pipeline

Two-phase adversarial review, productized.

Parallel read-only lanes emit candidate findings in a fixed format, then a fresh verifier per candidate returns confirmed, plausible, or refuted. The model that wrote the code never gets to be its only reviewer.

ui-audit

Branch-parity differ.

Compares a framework-upgrade branch against the staging environment screen by screen, so "the upgrade didn't change anything" is a diff, not a vibe.

How I work

A few rules from my workflow package, verbatim. I think they say more than a skills list would.

  • A gate that has only ever passed is a guess. Perturb what it should catch, confirm it fails with a readable diff and a non-zero exit, restore, confirm green.
  • A worker reporting "done" starts verification. It never ends the work. Verify diffs, runtime behavior, branches, and commits yourself. Never trust a summary.
  • A baseline that is not byte-identical across two runs of unchanged code is not a baseline. Flaky references make every comparison a coin flip.
  • Never present a skipped check as green. Every gate reports pass, fail, blocked, or not run, with the reason.
  • Smallest maintainable change that fully satisfies the request. A technically valid larger solution loses to an equally correct smaller one.
"Anything only I can judge is either real judgment or a missing gate. Mechanize the second kind."
